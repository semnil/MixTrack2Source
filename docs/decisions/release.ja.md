# リリースの決定

> For the English version, see [release.md](release.md).

リリースの手順について閉じた判断の記録。何を決めたか、理由、却下した案、決定を開け直す条件を書く。
手順そのものは [README.ja.md](../../README.ja.md) の「リリース」の節にある。

## プレリリースはリリースの手順に入れない

- **決定** (2026-10-20): リリースの手順が扱うのは `X.Y.Z` の形のバージョンだけ。プレリリースは手順に入れない
  - 手で push した `1.0.3-rc1` のようなタグをプレリリースとして扱うコードは残してある (`.github/scripts/release-tag-shape` と、`.github/workflows/push.yaml` の `create-release` ジョブ)。README は、これを手順としては載せていない
- **理由**: `cmake/common/bootstrap.cmake` が `buildspec.json` からバージョンを読み、`CMakeLists.txt` がそれを `project(VERSION)` に渡す。`project(VERSION)` は数字しか受け付けない。バージョンを `1.0.3-rc1` に変えるプルリクエストは、自分自身のビルドに失敗する
- **却下した案**:
  - `buildspec.json` にプレリリースのバージョンを書けるようにし、CMake には数字の部分だけを渡す。`cmake/common/bootstrap.cmake` に加えて、pkg・インストーラー・CPack のバージョンと、`.github/workflows/build-project.yaml` の成果物のパスまで変えることになり、大きな変更になる
  - 手で push する `X.Y.Z-rcN` のタグを、制約つきで README に載せる。パッケージの名前は `buildspec.json` のバージョンから付く。バージョンを変える前は、それは前のバージョンになる。変えた後は、そのバージョンのリリースタグが既にできている。どちらの順でも、筋の通った手順にならない
- **開け直す条件**:
  - プレリリースを再び求められたら、筋が通るのは 1 つ目の却下した案だけ。見積もる前に、バージョンを使う場所 (CMake・pkg・インストーラー・CPack・成果物のパス) を全部挙げる
  - リリースの経路を変えるときは、検査を組む前に、バージョンがどこへ渡るかを、使う場所の全部までたどる
- **うまくいかなかったことの記録**:
  - [#48](https://github.com/semnil/MixTrack2Source/pull/48) の検査 (フィクスチャのテストとミューテーション) は、シェルのステップの挙動だけを見ていた。層をまたぐ契約、つまりバージョンが `project(VERSION)` に届くことを見ていなかった。マージの直前のレビューがこれを見つけた。#48 の README は「プレリリースのバージョンを受け付ける」と書いていて、これは誤りだった。[#49](https://github.com/semnil/MixTrack2Source/pull/49) で直した
  - #48 からは、バージョンの変更をマージするとそのコミットにタグが付いてリリースのビルドが始まるので、「バージョンは変えたが、まだリリースしていない」状態が無くなった。最初の案の説明は、これを確かめずに書いたもので、案を選び直すことになった
